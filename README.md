# MiniDSP — 3-hour AI Developer Challenge (simplified)

**Objective:** Build a working, tested, documented MiniDSP web app using two GitHub Copilot chats and human judgement. This is a competition, not a compliance paperwork exercise.

## The entire workflow
1. Open the project in VS Code. Open GitHub Copilot Chat 1 in Ask mode (Instructor). Paste `START_HERE_INSTRUCTOR.md`.
2. Instructor proposes a small next task and gives a copy-ready prompt.
3. Paste that prompt into a separate GitHub Copilot Chat 2 in Agent mode (Developer). Agent implements, tests and records progress.
4. Paste Agent's response into Instructor. Instructor challenges assumptions, code, tests, security and gaps; gives a focused follow-up if needed.
5. Repeat until working; the human developer orchestrates, reviews and decides what to approve and when to commit/deploy.

**Don't paste raw uploaded file content, credentials or personal data into either AI chat.** Only synthetic training files may be used.

## Files
- `START_HERE_INSTRUCTOR.md` — paste once into Chat 1
- `START_HERE_DEVELOPER.md` — paste once into Chat 2, before its first task
- `PRODUCT_BRIEF.md` — functionality, safety and acceptance criteria
- `CHALLENGE_TIMELINE.md` — timeboxes and priority
- `DESIGN_REFERENCE.md` — facilitator fills in actual design-system paths and live URL
- `WORK_LOG.md` — Agent maintains short, honest progress/test/decision log
- `LEARNINGS.md` — Agent helps developer capture lessons
- `DEVELOPER_SCORECARD.md` — generated by the Agent at the end of the challenge only
- `FOR_SUNJEEV.md` — setup checklist and facilitator instructions
- `DEVELOPER_QUICK_GUIDE.md` — one-page instructions
- `tests/fixtures/` — starter synthetic files; optional withheld acceptance pack provided separately

The original exercise package was documentation only. This workspace now includes a Next.js App Router application, Supabase-backed upload/history, and the Milestone 3 product UI. See `WORK_LOG.md` for actual verification results and outstanding gaps; do not assume all database safeguards are complete.

## Run locally

- Node.js 24.19 or compatible; install the pinned packages with `npm ci`.
- Copy `.env.example` to `.env.local` and configure the dedicated development Supabase project locally. Never put real keys, test passwords, session cookies, or raw uploads in documentation or Git. No service-role key is used.
- Apply only approved migrations to your dedicated project. The database masking-hardening migration remains unverified; history responses withhold malformed stored examples rather than exposing them.
- `npm run dev` starts the application. Sign in, upload a synthetic CSV/TXT file, inspect the immediate masked result, then review the refreshed dashboard and findings.
- If corporate TLS inspection causes `SELF_SIGNED_CERT_IN_CHAIN`, use Windows' trusted CA store in the same PowerShell process:

```powershell
$env:NODE_USE_SYSTEM_CA='1'
npm run dev
```

The dashboard totals are calculated from the authenticated owner's stored scan records, not seeded samples. High-risk and Critical indicators count files by their highest classification; finding totals count occurrences. Recent scans show the newest five. Type and risk filters are combined and do not change dashboard totals. Dates use UTC.

`GET /api/scans` verifies the server-side session, explicitly scopes the query to the owner, reads database pages until complete, and returns a private/no-store response. The UI refreshes this history after a successful `POST /api/scans`. An unavailable history is shown as an error, never a zero-total success.

`GET /api/scans/export?type=<all|email|uk_phone|uk_nino|payment_card>&risk=<all|Low|Medium|High|Critical>` downloads the signed-in user's masked findings as CSV. Every field is quoted per RFC 4180, formula-leading cells (`= + - @ tab CR`) get a `'` prefix, and malformed stored examples are withheld. Unauthenticated requests get 401; unsupported filters get 400.

## Milestone 3 validation

```powershell
npx vitest run tests\workspace.test.tsx tests\scans.test.ts tests\history-route.test.ts tests\http.test.ts tests\pages.test.tsx
npm test
npx tsc --noEmit
npm run lint
npm run build
```

DOM interaction tests use React Testing Library and jsdom with mocked HTTP/session data; they do not prove RLS. To test real login, upload, and history against the running app and development database:

```powershell
$env:NODE_USE_SYSTEM_CA='1'
$env:MINIDSP_BASE_URL='http://127.0.0.1:3000'
npx vitest run --config vitest.integration.config.mts tests\integration\upload-e2e.test.ts
```

This real suite needs both local test accounts and creates synthetic scans. Do not rerun the separate RLS suite against the known weak schema until the approved hardening migration is applied; its negative test can persist the synthetic unmasked value when the guard is missing.

## Design references and gaps

The UI uses [design.md](./design.md) section 2's versioned Lepidus CSS/JS and `data-theme` shell, section 5's Button, Input, Card, Badge, Table, Radio, Message, Spinner and EmptyState anatomy, and section 7's token-based layout wrappers. No Tailwind or replacement UI library is used. Distribution is presented as accessible counts and risk badges, not a custom chart.

System gap: the contract has no dedicated native file-picker component. Upload uses a labelled native file input, descriptive help and the existing Button/Message components; it is not presented as a new Lepidus component. Mobile tables scroll inside labelled, focusable wrappers without restyling component internals. The responsive desktop breakpoint corresponds to the documented 1024px token; CSS variables cannot be used directly in media queries.

The approved-assets/live-reference fields in `DESIGN_REFERENCE.md` remain TODO. Browser checks cover layout at 390px/1440px and token resolution for light/dark/high contrast, not a full accessibility audit or design-owner approval. Runtime styling depends on the documented external design-system assets being reachable.
